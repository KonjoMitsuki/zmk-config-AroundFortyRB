## 1. 背景と目的

小型キーボードでは、記号・ファンクションキー・ショートカットの入力方法として、レイヤー切替とCombo（複数キーの組合せ）が候補となる。一方、どの操作を実際によく使い、どのキーの組合せなら意図しない発動や入力遅延が少ないかは、使用者自身の実測データを基に判断したい。

Windows／Linux／スマートフォンなど複数のホストで同じキーボードを使うため、**集計の正本はホストではなくキーボード本体（Central）**に置く。USBによる取得から始め、最終的にはBluetooth接続中にブラウザから無線で閲覧できることを目指す。

### 1.1 研究課題

1. どの**物理キー**・レイヤー・修飾キー付き出力・ショートカットがよく使われるか。
2. 通常のキー操作と衝突しにくいCombo候補はどれか。
3. `timeout-ms` や `require-prior-idle-ms` を変えると、**推定衝突リスク**はどう変わるか。
4. 意図したComboの**成立率**はどの程度か（通常打鍵からは評価できないため専用試験で測定）。
5. 同じ操作をレイヤーとComboで実現した場合、完了時間・操作回数・誤入力・主観負担はどう変化するか。

### 1.2 設計原則

- **日常の入力を優先**: 解析機能のために通常入力、Combo、トラックボール、左右分割通信を壊さない。
- **キーボード内で完結**: 端末変更やクラウドの有無に依存せず計測・累積する。
- **データ最小化**: 文章、パスワード、生のキー列、アプリ名、ウィンドウタイトルは保存しない。ただし集約統計にも残余リスクがあるため読出しを保護する。
- **推定と実測を混同しない**: 打鍵の衝突可能性は実際のCombo誤発動率ではない。
- **PoCで不確実性を潰す**: イベント順・USB共存・精度・保存余裕・認可APIの実現性を最初に測る。

## 2. 優先度とスコープ

| フェーズ | 優先度 | 機能 | 備考 |
|---|---|---|---|
| **技術検証（PoC）** | 最優先 | イベント観測位置と再投入時の計上、BLE側時刻、既存Studio USBの拡張可能性、RAM／フラッシュ余裕 | PoCが通るまでアーキテクチャを確定しない |
| **MVP** | 必須 | 左右の物理位置押下数、レイヤー別集計、限定ペアの時間差、最小限の出力・修飾キー集計 | 内部処理は有界・非ブロッキング |
| **MVP** | 必須 | 低頻度の永続化、電源再投入後の累計維持、保存失敗の検出 | 電源断直前の未保存分は許容 |
| **MVP** | 必須 | USB経由の統計スナップショット、記録一時停止・再開、全消去、読出し認可 | USB CLI可。ダッシュボードは不要 |
| **UI** | 高 | 静的Webダッシュボード、ヒートマップ、ランキング、JSON／CSV、タイミング品質表示 | Web SerialとJSON読込 |
| **Optimizer** | 高 | Combo候補の衝突推定・ランキング、専用試験モード、レイヤー比較 | 成立率は試験モードで取得 |
| **BLE** | 希望 | Web Bluetoothからの認可付きスナップショット取得 | Studio RPC拡張／専用GATTをPoC後に選択 |
| **将来** | 希望 | 長期比較・設定提案・他のZMKキーボード対応 | キーマップの自動書換えは対象外 |

**MVPの対象外**: クラウド／サーバー必須化、全キーイベントの生ログ保存、タイピング内容の復元、リアルタイム常時BLE送信、完全なアプリ別分析、キーマップ自動更新、任意のOS上でのWeb Bluetooth動作保証。

**段階的縮退の原則**: PoCでCombo成立識別などの上流フックが重いと判明した場合でも、物理位置カウント＋有限ペア統計＋USB読出しのMVPは独立して成立させる。ただし**物理キーの二重計上が排除できない限り、MVPとして完成扱いにしない**。

## 3. 機能要件

### FR-01 物理キー計測・計時精度

- 物理キーの**位置ID、押下／解放、イベントの単調時刻、発生元（Central／Peripheral）**を扱う。
- 位置ごとの押下回数を集計し、**有効レイヤー別の位置カウント**を併記する。レイヤーが複数有効な場合は「最高優先の有効レイヤー」など帰属規則を一意に定め、メタデータに含める。位置頻度と論理出力頻度を混ぜない。
- トラックボールの移動・スクロールは初期対象外。ボタン押下は後続の検討事項。
- キーの押下中状態、直近のイベントなど必要最小限の作業状態はRAM内のみ保持し、再起動や一時停止後に引き継がない。
- **キー入力時間の品質を3クラスに分類**する：
  - **C–C**: Central側の位置イベント同士（キーボード側のイベント時刻）。
  - **P–P**: Peripheral側同士（Centralが受信・再生成したイベント時刻）。
  - **C–P**: CentralとPeripheral間（異なる経路で得たイベント時刻）。
- ZMK `v0.3.0` の `app/src/split/central.c` はPeripheralの位置イベントを処理する際に `k_uptime_get()` でタイムスタンプを付ける。BLE構成では通知から内部キューを経由するため、これは電波の受信時刻そのものではない。Centralローカル側も `physical_layouts.c` でスキャンキューを取り出した時点の時刻を使う。**3クラスとも物理押下時刻との差／揺らぎを含む**。数msや20msのビンを無条件に高精度とは扱わず、実測した信頼可能な幅以上で評価する。
- BLE切断時には、押下中だったPeripheral位置の解放イベントが合成される。解放を実際の指の動きと断定せず、切断境界で重なり・idleの作業状態を破棄する。`physical_layouts.c` とBLE受信側には戻り値未検査の `k_msgq_put()` があるため、生成関数より前の欠落はこの観測点だけでは検出できない。未計装の欠落値は `null` とし、0を出力しない。
- Peripheralが切断中に押されたキーはCentralから観測できない。`internal_drop_count` は**観測可能な内部キュー溢れ等**の回数、`peripheral_disconnect_count`／`peripheral_disconnected_duration_ms` は**接続状態**として分離する。通信断期間中の**真の未観測打鍵数は不明**と表示し、0とはみなさない。
- 統計のレート正規化用に**アクティブ時間**を集計する。MVP案は「キー押下から30秒間をアクティブとみなし、隣接区間の重複時間は二重計上しない」。30秒は仮置きで、スリープ中・電源OFF中は加算しない。起動後のuptimeと、累積アクティブ時間を別管理する。
- 停止・スリープ・収集世代の終了ではその時刻でアクティブ区間を閉じる。スナップショット取得時には30秒の上限まで経過分を反映し、同じ区間を再度加算しない。ペアごとのレート分母も同じ収集境界に従う。

### FR-02 打鍵間隔・有限ペア統計

- 指定した2キーの**押下開始間隔**と**押下時間の重なり**を計測する。対象ペアは位置IDの順不同で一意に定義する。
- MVPでは**事前指定ペア**を優先する（例：16〜32ペア、設定可能）。全ペアの完全履歴は保持しない。後続で隣接キー自動生成やSpace-Saving等の候補選定を検討する。
- 暫定のヒストグラム境界は `0–20 / 20–40 / 40–60 / 60–80 / 80–100 / >=100 ms`。**C–C／P–P／C–Pで別に集計**し、精度検証後に細かさを決定する。信頼できない粒度の表示は統合または「参考値」にする。
- MVPの候補は「観測順で連続する2つの異なる位置の押下」とする。指定ペアに一致し、押下開始間隔が250ms未満ならN1へ加算する。先行キーがまだ押下中なら同じ候補をN2にも加算する。解放の介在はN1を除外せず、第三キーの押下が介在したA→C→BではA/Bを数えない。A→B→Aは異なる押下を終点とする2候補として扱う。この限定により、第三キーが介在する長い重なりは対象外となる。
- 押下中の同一位置への重複downは候補を作らず、品質カウンタへ記録する。OSのキーリピートは物理downではない。チャタリング除去は上流デバウンスに従い、Analyticsが時刻の近さだけで有効な再押下を除外しない。検出した欠落・逆行時刻・停止・切断では候補を破棄する。**これらの規則を集計実装前のテストで固定する**。
- **prior idleを2種類に区別**する：
  1. `physical_idle_ms`: 最後に観測した有効な物理**押下**から次の押下までの時間（研究・可視化用）。解放・合成解放・再投入を起点にしない。履歴のない区間先頭は不明とする。
  2. `zmk_combo_prior_idle_ms`: 実際のCombo判定に用いる直前キー時刻に対応する値（ZMK `combo.c` の非修飾キー／Combo時刻の管理を再現できた場合のみ）。
- ZMK `v0.3.0` の `require-prior-idle-ms` は単純な「最後の物理押下からの無入力時間」ではない。**物理idle値から効果を断定しない**。再現不能なら「近似」と明示する。
- 記録停止・再開、切断・復旧、データ世代切替の境界ではペア候補、押下中状態、prior idle履歴を破棄し、**境界をまたぐ組合せを生成しない**。
- 通常打鍵の近接・重なりから衝突リスクを推定する。**推定値 ≠ ZMKで実際に発生した誤発動率**とする（§7）。

### FR-03 修飾キー・ショートカット・レイヤー

- `keycode_state_changed` 等の論理イベントを用い、**修飾キーの状態**と**キーコード**の組合せを集計する。USB HIDとして実際に出る組合せ（推定）と、特定アプリで起きた動作を区別する。
- 初期対象: `GUI+SPACE`、`ALT+SPACE`、`GUI+V`、`LANGUAGE_1`／`LANGUAGE_2` 等。実際のOS・IME動作は接続先の設定に依存するため、操作名は「推定ラベル」とする。
- `&kp`、modifier-tap、macro、Combo経由の出力について**物理押下回数**とは別に**論理出力回数**を記録する。マクロが発行する各キーコードを「ショートカット1操作」とカウントするには、マクロ／行為単位の観測点または明示的な操作IDが必要なことを仕様に残す。
- レイヤーについて、有効化回数・滞在時間・物理位置との対応を計測する。**ユーザー操作由来**と**自動マウスレイヤー等の自動遷移由来**は可能な範囲で分離し、イベントだけでは区別できないときは `unknown` とする。根拠なく推測分類しない。
- hold-tapのタップ／ホールド判定結果は**任意の拡張機能**。MVPに必須とせず、軽量に計測できるフックがある場合に限って追加する。
- 接続先ホストのアプリやウィンドウは識別・記録しない。

### FR-04 Combo集計と観測位置

- 既存Combo（例：Q+W→Esc）と追加Comboについて、**実際の成立回数**を記録することを目標とする。キー出力を見ただけで成立Comboを断定しない。
- **重大な既知の課題**: ZMK `v0.3.0` の `app/src/combo.c` は位置イベントを `ZMK_EV_EVENT_CAPTURED` で捕捉し、Combo不成立時にはイベントを `ZMK_EVENT_RELEASE()` や `ZMK_EVENT_RAISE()` で解放・再投入する。`ZMK_EVENT_RAISE()` はイベント処理を先頭から再開し得るため、単にComboより前のlistenerで数えると**同じ物理打鍵を二重計上する危険**がある。
- **MVP必須条件**: 物理キーの1回の押下が、Combo候補化、成立／不成立、タイムアウト、キー先離し、別Comboとの重複のいずれでも**ちょうど1回**加算されること。二重計上またはカウント抜けが残る実装は採用しない。
- 候補方式をPoCで比較する：
  - (A) 入力生成元（Centralのマトリクス位置変換／分割イベント統合点）で一度だけ観測。
  - (B) イベント発行に一意識別子を付け、再投入を識別して重複排除。
  - (C) ZMKの既存listener機構とイベント進行状態で識別可能か確認。
  - (Aの実装候補) GNU linkerの `--wrap=raise_zmk_position_state_changed` により、新しいイベントの生成関数だけを観測する。`ZMK_EVENT_RAISE/RELEASE/RAISE_AT/RAISE_AFTER` はイベントマネージャーを直接呼び、この関数を通らない。`analytics/` のPoCはこの方式。監査済みソースの内容照合、LTO無効、Central限定を条件とし、最終ELFと回帰試験でフックの有効性を検証する。
- **listenerを先頭に追加するだけでは正確さを保証しない**。実際のリンク／サブスクリプション順、再投入時のコールパス、既存の左右分割処理をソース＋ビルド＋実機で固定する。
- Combo成立IDは標準のキー出力イベントだけでは識別できない場合がある。専用の軽量フック、または外部から識別可能な非侵襲な手段を検証する。MVPで成立計数を提供しない場合はその旨を明記し、見かけの出力回数で代替しない。
- 観測処理はイベントを消費せず、入力遅延を増やさない。有効時・無効時の入力挙動を回帰試験する。

### FR-05 永続化、USB取得、権限、操作

#### 5.1 保存と世代

- RAM上で随時集計し、**低頻度のバッチ保存**で不揮発領域に記録する。キー入力ごとのフラッシュ書込は禁止。
- 保存候補: アイドル移行、前回保存からの規定時間経過後、正常なスリープ直前、明示的な保存要求。**突然の電源断では最後の正常保存以降を失い得る**ことをUIに示す。
- 保存データに `schema_version`、世代番号、データ長、CRC等の検証情報を付与する。破損・電源断途中書込みを検出し、採用可能な直近世代へ復旧する。MVPでは最小二世代方式またはZephyr settings／ストレージ機構の性質に基づく同等方式をPoCで選ぶ。
- NVSではパーティション全体の空きだけでなく、**1レコードが1セクターに収まる上限**を確認する。分割保存する場合は全チャンクの世代・長さ・CRCを検証し、最後にcommitレコードを書いた世代だけを採用する。Bluetooth／Studio設定との共用容量、GC用空きセクター、保存コピー・転送コピー・スタックを含むRAM量を見積もる。
- 書込エラー回数、保存成功世代、保存状態（`ok`／`error`／`no_valid_snapshot`）を保持・取得する。
- カウンタ飽和は**無言のロールオーバー禁止**。MVPの推奨は `uint32` 飽和＋飽和フラグ。`uint16` の一部だけを半減して比率を歪める方式は採用せず、容量上必要なら全ビンを同一基準でスケールする方式を別途検証する。

#### 5.2 キーマップと物理配置の整合性

- `keymap_hash` だけでなく、**`physical_layout_id`／`mapping_revision`／`schema_version`** を区別する。
- **位置IDの意味に関わる変更**（マトリクス変換、物理レイアウト、position mapping等）があった場合、既存の物理位置統計を無条件に結合しない。
- **論理割当の変更**（レイヤー、Combo、マクロ、Studio経由の変更等）があった場合、物理位置の累計は維持できる場合があるが、論理出力とレイヤー別統計は新しい `mapping_revision` を持つ別世代として扱う。
- ビルド時の `keymap_hash` は比較材料の一つにすぎない。**ZMK Studio等による実行時の変更を検出できるかはPoCで検証**し、検出できない状態で「変更追跡済み」とは表示しない。変更が検出できない構成では、手動の世代切替／統計リセットを案内する。
- ハッシュの計算対象と正規化手順は実装時に公開し、ソースの単純なファイルハッシュを「実際に使用中の論理配置」と取り違えない。

#### 5.3 読出し・認可・物理操作

- MVPの**正規のデータ取得経路はUSB**。統計スナップショット取得、メタデータ取得、記録停止状態確認、全消去、必要な設定操作を提供する。開発初期はCLIでよい。
- **統計の読出し・エクスポート・リセット・設定変更はデフォルト拒否**。キーボード本体の明示的な物理操作による一時アンロックを要する。記録停止／再開自体は端末非依存にキーボード上で常時操作可能にする。
- アンロックは有限時間（初期案：60秒）で期限切れにし、切断・再起動・タイムアウトで失効させる。リセットはアンロックに加え、誤操作防止の再確認を行う。
- 既存キーマップには `&studio_unlock` があるが、**別途追加したCDCや独自RPCがStudioアンロックを自動継承するわけではない**。Studio APIに安全に連携可能かPoCで確認し、不可ならAnalytics専用の認可ゲートを実装する。
- **現行設定の制約**: R側confは `CONFIG_ZMK_STUDIO_LOCKING=n` であり、Studioは起動時からアンロック状態となる。また `studio/rpc.c` は要求ごとにStudioのidle timeoutを延長する。この状態・期限をAnalyticsの認可として流用しない。Analyticsには起動時ロック・物理操作起点の絶対期限を持たせ、ホスト要求で延長しない。設定可能なbehaviorだけで物理操作を担保する場合は、Studio経由でその割当を変更できることも設計に含める。
- **脅威モデル**: 通常のロック中に、接続ホストの任意アプリが無断で統計を取得することを防ぐ。**アンロック中の悪意あるホストプロセスを識別・排除できるとは主張しない**（物理アンロックはアプリごとの認証ではない）。接続端末自体が侵害されている場合の完全な保護は範囲外。
- 外部から読める「ロック中のステータス」は、プロトコル版、対応機能、ロック状態等の**機微でない情報だけ**に限定する。コマンドごとに認可を検査し、Transportの種類に依存しないポリシーにする。
- 記録一時停止はキーボード単体のトグル操作で可能とし、LED等の状態表示方法を決める。**停止時にはタイミング作業状態を破棄**。プライバシーの観点から再起動後も停止状態を維持する方針を基本とするが、設定保存と書込寿命の実現方法はPoCで確定する。
- **全消去**はRAM統計・保存済み全世代・候補ペア・試験モード集計を対象とする。消去後に旧世代から自動復旧しないよう世代管理する。
- 消去は保存ワーカーと直列化し、旧世代を無効化するreset epoch等を先に永続化する。完了応答は全対象の論理消去が成功した後に返し、途中電断・保存失敗時は成功と報告しない。消去前epochへの自動復旧を禁止する。通常APIで読めなくする論理消去と、フラッシュ残留データの物理消去を区別し、後者をNVSのキー削除だけで保証しない。

### FR-06 ブラウザダッシュボード

- **サーバー不要の静的Webアプリ**。キー配列のヒートマップ、キー／ショートカット／レイヤー頻度、時間差分布、Comboリスク評価、計測品質を表示する。
- USBはWeb Serial対応のChromium系ブラウザを主対象にし、ブラウザ非対応環境では**CLIが出力したJSONファイルを読み込める**ようにする。Web Serialに対応していてもデバイス列挙や権限はOSに依存する。
- **接続中はダッシュボードが常に統計を読めるわけではない**。アンロックされていない場合は明確なガイドを表示し、取得不可を正常なセキュリティ状態として扱う。
- CSV／JSONエクスポートは、`schema_version`、`device_id`（ランダム・匿名識別子か省略）、`physical_layout_id`、`mapping_revision`、統計の種類・精度クラス・収集条件を含む。初期状態では公開アップロードを行わない。
- 実測／推定／試験モード／サンプルデータの表示を明確に区別する。測定困難なP–P／C–Pの時間幅は警告または参考値扱いにする。
- ショートカットランキングは**HID出力の集計**であり、「ホストのアプリに何の操作が実行されたか」とは一致しない場合があると記す。

### FR-07 Bluetoothブラウザ閲覧（後続フェーズ）

- Web Bluetooth対応環境で、BLEにより**キーボード内の集計済みスナップショット**を取得できることを目指す。リアルタイム全打鍵イベント配信は対象外。
- 候補：ZMK Studio RPC経路の拡張／Analytics独自BLE GATTサービス。選定は通信仕様・認可・接続維持・コード保守性をPoCで比較した後に行う。
- Bluetooth HID接続とAnalytics用通信が**同じホストで共存できるか**、別ホストからの同時接続の可否、ペアリング・接続権限、OS・ブラウザ差異を実機で検証する。
- BLEでもFR-05のアンロックが必須。ペアリング済みであること**だけ**を認可の代わりにしない。切断・失効時のデータ転送途中終了を安全に扱う。
- BLE未対応の端末でもUSB・JSON読込を正式な代替手段として維持する。

### 4.1 プライバシー・セキュリティ

- 生の文字列、連続したキー列、パスワード、ウィンドウタイトル、アプリ名、入力先URLは**保存しない**。3キー以上の順序付きシーケンスを永続化しない。
- 長期間の位置／ペア統計でも入力内容が一部推測され得るため、ペア数・精度・保持期間を限定する。**パスワード欄を自動判別できる前提を置かず**、キーボード側の記録停止を提供する。
- アンロック操作は読出し・消去等の認可に使い、**記録停止操作とは別**にする。停止中のカウンタ・履歴の状態遷移をテストする。
- BLEでは暗号化接続・ペアリング権限を別途検討しつつ、物理アンロックを必須の追加条件とする。
- データをブラウザ内に蓄積する場合は明示的な保存操作を前提とし、第三者サーバーへの送信をしない。エクスポート時には集計値も機微性がある旨を表示する。

### 6.2 通信プロトコル要件

- 要求／応答コマンド（例：`GET_CAPABILITIES`、`GET_SNAPSHOT`、`GET_STATUS`、`RESET_STATS`、`SET_RECORDING`、`GET_CONFIG`）の**認可要否**と応答を明示する。`GET_CAPABILITIES` など公開可能な情報以外はロック中に出力しない。
- バージョニング、メッセージID、エラーコード、最大サイズ、タイムアウト、リトライ、再接続時の扱いを定義する。
- 大きなデータは分割取得し、全体の**スナップショット世代と整合性**を検証してから採用する。分割送信中に統計が更新されても混在させない（読み出し時に固定スナップショットを用意する、または世代を再検証する）。
- CRCはデータの**偶発的破損の検出**に用いるものであり、認証・改ざん防止を提供しない。既存Studio RPCのフレーミング／整合性保護が十分であれば重複CRCを強制しない。新規独自フレーミングの場合はCRCを付ける。
- 通信路ごとに実装が異なっても、権限・論理スキーマ・集計値の意味を共通化する。
- USB接続の瞬断、BLE切断、認可期限切れでは途中データを**不完全として破棄**し、必要なら再取得する。

## 7. Combo候補評価

評価軸は、通常打鍵との衝突可能性、押しやすさ、必要指数、既存キー／hold-tapとの競合、割当先操作の使用頻度・重要性、推定精度とする。

### 7.1 評価指標の定義

事前指定ペア `{A, B}` と時間閾値 `T`（ms）について、**同一の観測可能な打鍵区間内**にある2キー押下を候補イベントとして扱う。候補ペアの順番はA→BとB→Aを両方許し、**一つの物理的な組合せは一度だけ計数**する。通常入力のスキャンデータを永続化せず、イベント到着時に有界ヒストグラムへ加算する。

MVPの候補抽出はFR-02の連続押下規則に従う。ビンは左閉右開区間とし、末尾の `100+` はMVPでは `[100,250)` を意味する。250ms以上は候補外とする。保存済みヒストグラムから正確に再集計できる閾値は20／40／60／80／100／250msに限る。任意の30ms等を表示する場合は上下限として示し、ビン内の分布を勝手に補間しない。これらの数値は実機の精度検証で改定する。

- **近接押下数 `N1(T)`**: AとBの押下開始時刻の差の絶対値が `T` 未満の候補数。
- **重なり近接数 `N2(T)`**: `N1(T)` のうち、先に押したキーが離される前にもう一方が押された候補数。
- **押下正規化リスク `R_press(T)`**: `N2(T) / (count(A)+count(B)) * 1000`（対象キー1000押下あたりの重なり近接候補数）。両方の押下数が0なら未定義。
- **時間正規化リスク `R_hour(T)`**: `N2(T) / active_hours`（アクティブ1時間あたり）。アクティブ時間0なら未定義。
- **条件付きリスク `R_idle(T, I)`**（後続）: ZMKのprior idle条件 `I` を満たした候補に限定した上記指標。`zmk_combo_prior_idle_ms` の再現・精度確認が必要。

分母は対象ペア・mapping revision・収集条件が同じ区間の押下数とアクティブ時間を使う。ペア追加以前や停止中の時間、維持した物理位置の生涯累計を混ぜない。`R_idle` は時間差とidleの**同時分布**または条件ごとの専用カウンタが必要であり、別々の周辺ヒストグラムだけからは計算しない。飽和したカウンタからは確定的な比率を出さない。

これらは**Combo成立可能性を単純化した代理指標**であり、`require-prior-idle-ms`、イベントの再投入、他Comboとの候補競合、レイヤー、解放順、hold-tap処理などZMKの完全な判定を再現しない。C–C／P–P／C–P別に算出し、P–P／C–Pの細かな閾値は精度検証で使用可否を決める。

### 7.2 評価対象

- 初期対象操作: 記号 `()` `{}` `[]`、Esc、Tab、Win+Space、Alt+Space、IME切替、GUI+V。
- F1–F12は全てCombo化することを初期目標にせず、レイヤー入力と比較する。
- 優先順位は**利用頻度 × 推定衝突リスク × 操作負荷**を参考にする。ただし運動負荷は物理配列・指使いの推定であることを表示し、使用者の実測／主観評価を優先する。

### 7.3 Combo試験モード（Optimizer段階）

- 指定Comboを**意図してN回実行する**試験を用意し、試行回数・実際の成立回数・入力所要時間・再試行・押下間隔を集計する。
- **成立率 = 成立回数／有効試行回数**。トライアルの開始と終了を明示し、通常統計と混ぜない。中断・誤操作・計測欠落は別に示す。
- 試験モード中はキーボード・ダッシュボード双方で状態を表示し、必要なら安全なテスト用レイヤー等で入力先への影響を最小化する。
- 成立判定はファームウェアのCombo識別フック等によって行い、最終出力文字の一致だけでは代用しない。

### 8.2 MVP完了条件

1. Analytics有効／無効ビルドで、文字入力、既存Combo、hold-tap、レイヤー、トラックボール、左右通信、Studioの従来機能に**機能退行がない**。
2. **台本テストにおける物理キー押下の二重計上0**。Centralの観測可能な位置カウント欠落0、分割通信時の内部欠落率は合意した基準以下（初期案≤0.1%）。Peripheral切断中の未知欠落は「不明」と表示する。
3. 指定ペアのC–C／P–P／C–P集計、レイヤー別位置カウント、主要な論理出力が確認でき、推定精度の分類が出力される。
4. Windows・Linux等の複数ホスト利用が**1台のキーボード内の累積値**として記録され、再起動・通常スリープ後も正常保存済みの値が残る。強制電源断では直近未保存分のみ失う可能性を明示する。
5. USB経由の統計読出しは**ロック中拒否／物理アンロック後のみ許可／期限切れで再拒否**となる。全消去は確認操作後に実行できる。
6. キーボード単体の記録停止／再開が機能し、停止中の集計停止、タイミング履歴破棄、再起動時の停止状態の扱いが仕様どおりである。
7. マッピングを変更したとき、追跡可能な変更は新しい世代に分かれ、未追跡の変更については**追跡済みと偽らない**。
8. §4の性能・RAM・フラッシュ・電力をON/OFFで測定し、仮目標との差と採用判断を記録する。保存破損の復旧とカウンタ飽和をテストする。

### 8.3 後続フェーズ完了条件

- **UI**: ローカルの静的Webアプリでヒートマップ・ランキング・精度警告を表示し、JSON読込・エクスポート・権限エラー表示ができる。
- **Optimizer**: 閾値別の推定衝突リスクを再現可能な条件で比較し、試験モードの成立率を通常統計と分けて表示できる。
- **BLE**: 対応環境でHID利用と認可付き閲覧が共存し、未対応／切断／ロック時にはUSB・JSONへフォールバックできる。

### 8.4 最低限の回帰試験マトリクス

| ID | シナリオ | 必須の確認結果 |
|---|---|---|
| T01 | Comboを使わない単独キーを押下・解放 | 押下1回、解放時に追加加算なし |
| T02 | `Q+W` で既存Esc Combo成立 | Q・Wの位置押下は各1回、Combo成立計測があれば1回 |
| T03 | Qの後、Wがタイムアウト／先離しで不成立 | 元キーを2重計数しない、通常出力を壊さない |
| T04 | Combo候補へ第三キーが介在／別Comboと競合 | 再投入イベントの重複なし |
| T05 | 左だけ／右だけ／左右交差の規定打鍵 | 3つの計時精度クラスを区別、精度の限界を記録 |
| T06 | Peripheral切断・再接続 | 未観測打鍵数は不明、接続障害を表示 |
| T07 | 計測を停止→入力→再開 | 停止中は加算なし、停止前後のペアを作らない |
| T08 | ロック中の読出し・リセット要求 | データ漏出も消去も起こらない |
| T09 | アンロック→取得→期限切れ | 期限切れ後は再拒否、接続切断でも失効 |
| T10 | 保存中の電源断・破損した世代 | 完全な旧世代に復旧、失敗を報告 |
| T11 | キーマップ／物理配置の変更 | 適切な統計世代切替、未検出なら明示 |
| T12 | Analytics ON/OFF比較 | キー入力、トラックボール、Studio、性能の回帰なし |
| T13 | カウンタ上限到達の模擬 | ラップアラウンドせず飽和状態を表示 |
| T14 | 長時間使用・スリープ・再起動 | アクティブ時間・保存済み累計が定義どおり |

## 9. 開発順序

1. **PoC-A: イベント正確性** — `combo.c` の捕捉／再投入を踏まえ、計測点を選定。T01〜T05を最小ビルドで通す。ここが不合格なら集計機能を拡張しない。
2. **PoC-B: 精度とハードウェア予算** — C–C／P–P／C–Pの実測、RAM／フラッシュ計測、待機電力と連続打鍵電力のベースラインを採取。
3. **PoC-C: USB通信・認可** — 既存Studio USB経路を試し、HID共存、拡張可能性、アンロックAPIを確認。必要なら代替CDCを試す。
4. **MVP-1: 集計実装** — 位置・レイヤー・指定ペア・物理idle・限定HIDショートカット統計を有界メモリで実装する。
5. **MVP-2: 永続化・安全操作** — 保存世代、CRC／同等の破損対策、記録停止／再開、全消去、マッピング世代、物理アンロックを実装する。
6. **MVP-3: CLIと回帰テスト** — USB取得・JSON出力、T01〜T14、ビルドON/OFF差分を整備する。
7. **UI** — 静的Webアプリ、Web Serial接続、JSONフォールバック、精度・警告表示。
8. **Optimizer** — Combo推定・ランキング、成立率試験、レイヤーとの比較実験。
9. **BLE** — Studio RPCまたはGATTを選定し、対応環境で閲覧・認可・HID共存を検証。

### 9.1 研究の比較実験設計

- 同じ課題セット（プログラムの記号入力、日本語／英語切替、ショートカット）を**レイヤー方式／Combo方式**で行い、順序を入れ替える（カウンターバランス）。
- 各条件に練習期間を設け、慣れによる影響を減らす。
- 指標：課題完了時間、操作回数、誤入力率、実際のCombo誤発動／不成立、主観的疲労、覚えやすさ。
- 対象者は当面本人のみ。**個人最適化の検証であり一般化可能な有意差を主張しない**。
- キーマップ変更・設定の条件、ZMKバージョン、タイミング品質、練習量を実験メタデータとして保存する。入力文字列そのものをキーボードに記録する必要はない。

## 11. リスク一覧

| リスク | 影響 | 低減策／判断 |
|---|---|---|
| **Combo再投入による二重計上** | 頻度・リスク推定が無効になる | 入力生成元の観測または一意ID導入、T01〜T04必須 |
| **Peripheral到着時刻の揺らぎ** | P–PとC–Pで閾値推定が不正確 | 精度クラス分離・実測・粗いビンまたは参考値扱い |
| **通信断中の未観測入力** | 真の打鍵数を過小評価 | 不明値として表示、接続時間を別記録 |
| **Studioによる動的変更未検出** | 異なるレイヤー統計が混在 | Mapping revision追跡、未検出なら手動切替＋警告 |
| **アンロック中のホスト側プロセス** | 統計読出し・操作の機会 | 短時間アンロック、機能別権限、脅威モデルを明示 |
| 計測処理の遅延・消費電力 | 日常入力に支障 | ホットパス非ブロッキング、ON/OFF計測、Kconfig無効化 |
| RAM・フラッシュ不足 | 計測範囲の縮小が必要 | 有界集計、候補ペア数の上限、保存容量上限 |
| フラッシュの摩耗・書込み中断 | 統計破損、電池への影響 | バッチ化、世代管理、電断復旧試験 |
| カウンタ飽和 | 数値が誤って見える | 飽和処理、フラグ、エクスポート警告 |
| ZMK上流更新 | イベント順・通信API変更 | バージョン固定、CI、回帰テスト |
| ブラウザ機能非対応 | 一部端末で表示不可 | CLI、JSONファイル、USB経路を維持 |
| 集約統計のプライバシー | 打鍵傾向を推測される | 物理停止・アンロック・全消去・ローカル処理 |

## 12. 用語集

- **Central / Peripheral**: ホストに対してHID入力を統合する側／その側へ入力を送る分割キーボード側。
- **C–C / P–P / C–P**: 2キー計時の入力経路別分類。Central同士／Peripheral同士／左右跨ぎ。
- **Combo**: 複数位置キーの短時間内の押下を別の動作に割り当てる機構。
- **Combo成立**: ZMKのCombo処理が対象Comboのbehaviorを発動した事実。通常のキー出力一致とは区別。
- **イベント捕捉・再投入**: Combo等が処理を保留し、その後イベントを後続または先頭から再配信すること。
- **`physical_idle_ms`**: 観測された有効な物理キー押下同士の間隔。解放を起点にしない。
- **`zmk_combo_prior_idle_ms`**: ZMK Comboのprior idle判定に整合するよう再現した論理入力起点の間隔（再現できる場合のみ）。
- **`physical_layout_id`**: 物理位置IDと実際のキー位置の対応を識別するID。
- **`mapping_revision`**: レイヤー／behavior／Combo等の論理割当の版。実行時変更の追跡可否に依存。
- **`keymap_hash`**: ビルド時等のキーマップ識別子。実行時の実際の設定を単独で保証しない。
- **アクティブ時間**: 仕様に定義した「使用中」とみなす区間の合計。接続時間・uptimeとは区別。
- **`internal_drop_count`**: Central側で実際に検出できた内部処理の欠落件数。通信断中の実際のキー入力数ではない。
- **PoC**: Proof of Concept。詳細実装前に、計測・通信・保存の技術成立性を確認する試験。
